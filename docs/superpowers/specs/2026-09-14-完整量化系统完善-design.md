# 完整量化系统完善 - 设计规范

> 日期：2026-09-14
> 状态：已与用户确认，进入实现计划阶段

## 1. 背景与目标

当前项目已具备完整的微服务架构骨架（6 个 FastAPI 服务 + Vue3 前端 + Docker 编排 + common 公共模块），各服务 main.py 已注册路由、引擎模块（trading/risk/backtest/portfolio）已实现核心逻辑、服务间已有部分 httpx 集成、认证/WS/调度器/Prometheus/Alembic 基建齐备。

但项目**尚不能真正运行**，且存在以下核心缺口：

- 服务启动即崩溃：`SECRET_KEY` 默认值不满足自身校验（<32 字符）；data-service 模型缺 `Boolean` 导入
- 依赖缺失：`pydantic-settings`、`psutil`、`redis` 未进 requirements，docker 构建必然失败
- 数据库表未建：dev compose 未跑 alembic，仅 data-service 调 `init_db` 且只建自身 3 张表
- **闭环断裂**：strategy-engine 调度器无实际 job（不喂 bar）、信号不落库、信号不下单 => 市场数据到持仓的完整链路不通
- 内部服务鉴权：trading → risk `/check` 不带 token 被 401 拦截，风控形同虚设
- 交易/持仓引擎纯内存态：重启即丢
- 测试基建为桩（conftest 不加载真实服务），CI/测试全红

**本次目标（用户已确认）：**

1. 后端真正跑起来、打通「行情 → 策略 → 信号 → 订单 → 风控 → 持仓」闭环（方案 A：同步 HTTP 桥）
2. 交易/持仓持久化落库（重启不丢）
3. 关键链路自动化测试 + 手工 E2E 验证
4. 前端体验同步完善（图表、WS 推送、加载/空态）
5. 不含生产部署完善（prod compose 缺失文件暂不动）

## 2. 设计决策

| 决策点        | 选择                                                                             | 理由                                             |
| ------------- | -------------------------------------------------------------------------------- | ------------------------------------------------ |
| 信号→订单联动 | 同步 HTTP 桥（strategy-engine 回调后 POST trading-service）                      | 与现有集成模式一致，易测可观测；模拟撮合性能足够 |
| bar 喂入      | strategy-engine scheduler 真实 job：启动预热 klines + 每 30s 拉 quote 转 BarData | 复用现有 `manager.process_bars`                  |
| 信号持久化    | `emit_signal` 写 `common.models.strategy.StrategySignal`                         | 前端信号流可见                                   |
| 内部服务鉴权  | `risk /check` 改 `get_optional_user`                                             | 避免内部调用被 401 截断                          |
| 持久化        | 交易/持仓引擎内存为快路径 + DB 为持久真相，双写                                  | 重启可重建                                       |
| 建表          | 每服务 lifespan 调 `common.init_db()`（create_all 幂等）                         | dev 无需手工 alembic                             |
| 测试          | 重写 conftest 加载真实 app + SQLite override + httpx mock；关键链路测试为主      | 证明闭环成立                                     |
| 生产部署      | 本轮不动                                                                         | 用户选择后端先行、部署暂缓                       |

## 4. 详细设计

### 4.A 稳定运行修复（崩溃根因）

1. **SECRET_KEY 修正**
   - `services/common/config.py`：`SecurityConfig.SECRET_KEY` 默认值改为 `dev-secret-key-0123456789-abcdefgh`（≥32 字符）；生产环境校验逻辑保留
   - `.env.example`：`SECRET_KEY=...` 改为 `SECURITY_SECRET_KEY=...`（注意 `SecurityConfig.env_prefix="SECURITY_"`，当前文档变量名永不生效）
   - `docker-compose.yml`、`docker-compose.prod.yml`：注入 `SECURITY_SECRET_KEY`（dev 用默认值，prod 用 `.env` 变量）
2. **data-service 模型修复与统一**
   - 删除 `services/data-service/app/models/market.py` 与 `services/data-service/app/database.py` 中的独立 `Base`
   - `app/routers/market.py` 改从 `common.models.market` 导入 `MarketData/StockInfo/Calendar`
   - `app/main.py` 的 `init_db` 改用 `common.init_db()`（`common.database.Base` 统一建表，含全部服务表）
3. **依赖补齐（进入各服务 requirements.txt）**
   - `pydantic-settings`（config.py 依赖）
   - `psutil`（health.py 依赖）
   - `redis`（common 全量导入 redis_client，所有服务必需）
   - 根目录新增 `requirements-dev.txt`：全部服务依赖 + 测试依赖（供 CI/本地测试）
4. **建表兜底**：每个服务 lifespan 调用 `common.init_db()`（幂等 create_all）
5. **内部鉴权**：`services/risk-service/app/routers/risk.py` 的 `POST /check` 改 `get_optional_user`
6. **tushare token**：`services/data-service/app/routers/market.py` 中 `TushareDataProvider(token=settings.tushare.TUSHARE_TOKEN)`

### 4.B 闭环打通

1. **bar 喂入（strategy-engine）**
   - 策略 `run` 时：`data_client.get_klines(code, 近一年)` 预热 `strategy.update_bar_history`
   - `lifespan` 注册 scheduler job `feed_bars`（IntervalTrigger 30s）：遍历运行中策略 → `data_client.get_quote(code)` → 转 `BarData` → `strategy_manager.process_bars`
2. **信号落库**
   - 在 strategy-engine 增加信号持久化逻辑：策略 emit 后写 `common.models.strategy.StrategySignal`（strategy_id 转 int，signal 字段映射 action/code/price/quantity/reason/strength）
3. **信号→订单桥**
   - 策略启动时向 `strategy_manager.register_signal_callback` 注册执行器：
     - 过滤 `action != hold`
     - 去抖：同一 code + action 在去抖窗口（如 60s）内不重复下单
     - `POST http://trading-service:8003/api/v1/trading/order`，payload：`code/direction/order_type=limit/price/quantity(strategy 给出的 quantity)/strategy_id`
   - `quantity` 规则：buy 使用信号 quantity（需为 100 的倍数，非整百按整百向下取整，最少 100）；sell 由策略 signal 提供（策略维护自身持仓）
4. **闭环回查**：成交 → trading 引擎已有同步 `portfolio-service /process-trade` 逻辑（保留）

### 4.C 交易/持仓持久化

1. **trading-service 引擎持久化**
   - `create_order` 时：写 `common.models.order.Order`（status=pending）
   - `_simulate_fill` 成交后：写 `common.models.order.Trade` + 更新 Order 状态（filled/数量/均价）
   - `cancel_order` / `check 拒绝`：更新 Order 状态
   - 启动时 `initialize()`：从 DB 读取 orders/trades → 重放 trades 重建持仓、资金（初始资金从首笔 deposit 或默认 100000 标注）
2. **portfolio-service 引擎持久化**
   - `process_trade` / `deposit` / `withdraw`：写 `common.models.portfolio.{Position, Account, AccountLog}`
   - 启动时恢复：读取 Account、Position、AccountLog 重建内存态
3. **risk-service 检查记录**：`check` 通过后写 `common.models.risk.RiskCheck`（order_no 可为空）；限额启动时读取或加载默认值
4. 一致性原则：内存为快路径读，DB 为持久真相；以路由调用引擎方法处为写入点，不引入复杂事务

### 4.D 测试与验证

1. **conftest 重写**
   - SQLite 内存库 + `common.database.Base.metadata.create_all`
   - 每个测试加载对应真实服务 `app`（如 strategy-engine app.main），`dependency_overrides` 注入 `get_db`
   - httpx 服务间调用 mock（`resp` 桩或 monkeypatch `httpx.AsyncClient`）
   - 内部鉴权：`auth_service` 用测试密钥初始化并生成测试 token，或直接 override `get_current_user`
2. **新增测试文件**
   - `tests/test_auth.py`：注册/登录/me/401
   - `tests/test_strategy_api.py`（修复现有）：CRUD + 信号链路（emit→落库→查询）
   - `tests/test_trading.py`：订单创建→提交→风控 mock 放行/拦截→成交→持仓/资金变化；重启恢复
   - `tests/test_risk.py`：限额检查（超限/放行）、VaR
   - `tests/test_portfolio.py`：process_trade 多笔重建、入金出金、恢复
   - `tests/test_backtest.py`：创建→mock 数据驱动引擎跑通→结果持久化查询
   - `tests/test_data_service.py`：quote/kline/stocks/calendar（mock provider）
3. **手工 E2E**
   ```
   docker-compose up -d
   register → login → 建 strategy(dual_ma, active) → run
   → 观察 /strategy/{id}/signals 出现信号
   → 观察 /trading/orders 自动订单、/portfolio/positions 持仓更新
   → 建 backtest 用 mock 数据 → 出权益曲线
   ```
4. **CI**：改为 `pip install -r requirements-dev.txt`，测试命令不变

### 4.E 前端同步完善

1. **Dashboard.vue**：资产卡片 + 权益曲线（调用 `/portfolio/analysis` 或回测曲线）+ WS 订阅 `market.quote`
2. **Market.vue**：股票搜索 + K 线 ECharts + 加载/空态
3. **Trading/Portfolio/Risk/Backtest**：加载态、空态、错误提示、操作反馈
4. **公共组件**：`src/components/StockChart.vue`（K 线）、`EquityCurveChart.vue`（权益曲线）、`PositionsTable.vue`、`MetricCard.vue`
5. **useWebSocket composable**：订阅/重连/按频道分发
6. 验证 `npm run build` 通过

### 4.F 治理收敛（不含生产部署）

1. dev compose：注入 `SECURITY_SECRET_KEY`；各服务 `restart: unless-stopped` + healthcheck；redis volume
2. `requirements-dev.txt` 统一依赖；各服务 requirements 与本地版本收敛（fastapi/sqlalchemy/pydantic/pydantic-settings/psutil/redis 等）
3. 生产 compose 缺失文件（Dockerfile.prod / monitoring / ssl / init_db.sql）**不在本轮范围**，留后续

## 5. 阶段与依赖顺序

R1. 稳定运行修复（config/data-service 模型/依赖/建表/鉴权/tushare）—— 必须先做，否则全部阻塞
R2. 闭环打通（feed_bars / 信号落库 / 订单桥）
R3. 持久化（trading/portfolio/risk 引擎→DB）
R4. 测试（conftest 重写 + 各服务测试）
R5. 前端（组件/页面/WS/build）
R6. 治理与收尾（compose/requirements/CI、E2E 手验）

R1→R2→R3→R4→R5→R6 强依赖顺序；R4 可与 R2/R3 交叉验证。

## 6. 验证标准

- [ ] `docker-compose up -d` 后 6 服务全部 healthy，`/health` 均 200
- [ ] 注册/登录拿 token，受保护路由无 token 返 401
- [ ] 建策略 → run → `/strategy/{id}/signals` 出现信号
- [ ] 信号自动生成订单 → trading/orders 有记录 → portfolio/positions 持仓更新
- [ ] trading/portfolio 重启后状态保留（持久化）
- [ ] 回测 end-to-end 成功并返回权益曲线
- [ ] `pytest` 通过（关键链路覆盖），CI 测试 step 绿色
- [ ] `npm run build` 前端构建通过
- [ ] 无 token 内部调用（trading→risk）不因 401 阻断（`get_optional_user`）
